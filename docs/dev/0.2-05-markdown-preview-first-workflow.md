# Markdown 预览优先工作流设计

| 字段 | 内容 |
| --- | --- |
| 状态 | Superseded（由 [`0.2-06`](./0.2-06-markdown-last-view-continuity.md) 取代） |
| 日期 | 2026-08-05 |
| 目标 | 将当前 Markdown 强制双面板改造为“默认阅读，需要编辑时展开双面板”的智能工作流 |

## 1. 结论

建议采用“预览优先、按需编辑”的两态设计：

1. 普通打开 Markdown 文件时，默认只显示渲染后的预览，最大化阅读空间。
2. 用户表现出编辑意图时，将当前文档展开为源码与实时预览双面板。
3. 用户可以通过设置将默认打开方式改为双面板。
4. 阅读态下，整个 VS Code 编辑区严格保持 1 个编辑器组；编辑态下严格保持 2 个编辑器组，以在有限空间内获得确定且最佳的视觉效果。

本文所称“面板”均指 VS Code 的 **editor group（编辑器组）**，不是终端、输出等底部 Panel。其他已打开标签页可以保留，但必须安全合并到目标编辑器组中，不能继续占用额外并排空间。

这比当前“任何 Markdown 源文件激活后立即强制双面板”的行为更符合阅读优先的使用场景，同时通过固定的 1/2 组布局保证预览和编辑空间。

为避免与 VS Code 自身的“预览标签页（preview editor）”概念混淆，本文使用以下术语：

- **阅读态（Rendered Preview）**：仅显示渲染后的 Markdown 预览。
- **编辑态（Edit with Preview）**：同时显示源码编辑器和实时预览。

## 2. 改造前实现及问题

改造前的实现位于 `src/markdownDualPane.ts`，由活动文本编辑器变化触发，并执行以下操作：

- 将源码放入 Group 1，将内置 Markdown 预览放入 Group 2；
- 关闭 Group 1 和 Group 2 之外的编辑器组；
- 强制恢复 Group 1 为活动组；
- 使用布尔设置 `quicklook.markdownDualPane` 控制启停。

主要问题：

- 阅读 Markdown 时始终占用两个面板，预览空间不足。
- 布尔设置只能表达“启用或禁用”，无法表达“预览优先”与“默认双面板”两种产品模式。
- 仅凭活动文本编辑器变化触发布局，难以区分首次打开、主动编辑、Diff 查看和历史文件查看。
- 当前只尽力迁移普通文本标签页，尚未系统保证 Diff、自定义编辑器、终端标签和未保存内容在收拢编辑器组时都能安全保留。
- 改造前的最低版本仍为 VS Code 1.91，无法把 VS Code 1.131 的现行 Markdown 原生交互作为明确基线。

## 3. 目标交互

| 场景 | 预期行为 |
| --- | --- |
| 普通本地 Markdown 首次打开，默认设置为 `preview` | 进入阅读态：整个编辑区收拢为 1 个编辑器组，只显示当前文档的渲染预览 |
| 阅读态下点击原生 “Reopen as source file” | 静态预览在当前组恢复为源码；插件随后调用原生侧边预览，进入严格 2 组编辑态 |
| 默认设置为 `dualPane` | 文件打开后直接进入编辑态，并严格保持 2 个编辑器组 |
| 源码编辑器点击原生 “Open as Preview” | 源码在当前组重开为静态预览；插件关闭重复的侧边预览并收拢为严格 1 组阅读态 |
| 源码编辑器点击原生 “Open Preview to the Side” | 在新组打开动态预览；插件确认并规范为源码加预览的严格 2 组编辑态 |
| 侧边预览点击原生 “Open Source File” | 不改变双组布局，仅将焦点交还原源码编辑器组 |
| 编辑态下手动关闭源码 | 回到阅读态，收拢为仅包含当前预览的 1 个编辑器组 |
| 编辑态下手动关闭预览 | 仍属于编辑态；插件恢复当前预览并重新规范为 2 个编辑器组 |
| 模式切换前已存在更多编辑器组 | 先安全保留其中的标签页，再合并多余编辑器组，最终达到目标数量 |
| 打开 Diff、SCM、Git 历史或只读虚拟文档 | 默认保留 VS Code 原生视图，不自动重排；后续如有明确需求再单独设计 |

VS Code 原生 Markdown 预览已经支持源码与预览切换、侧边实时预览和滚动同步。因此应复用原生能力，不创建自定义 Webview 或重新实现 Markdown 渲染。

编辑态的第二组必须由原生 `markdown.showPreviewToSide` 直接创建，以遵循 `workbench.editor.openSideBySideDirection`：`right` 时源码在左、预览在右，`down` 时源码在上、预览在下。插件不得先预建两列或两行再调用该命令，否则 `down` 会在已有两列之外新增第三个空白组。对于经常在显示器半屏中使用 VS Code 的场景，推荐设置为 `down`。

## 4. 设置设计

删除现有布尔设置：

```text
quicklook.markdownDualPane
```

改为枚举设置：

```json
{
  "quicklook.markdownOpenMode": "preview"
}
```

允许值：

| 值 | 行为 |
| --- | --- |
| `preview` | 默认值。普通打开时进入阅读态，需要编辑时展开双面板 |
| `dualPane` | 普通打开时直接进入编辑态 |

不保留旧设置的兼容层、回退读取或迁移逻辑。设置名称和行为变化应在 README 与 CHANGELOG 中明确说明。暂不增加 `source`、方向、比例等额外配置；只有出现真实需求后再扩展。

## 5. 编辑意图与状态转换

不能把任何焦点变化都视为编辑意图。建议为每个 URI 维护会话级状态，并只允许阅读态与编辑态两种受控状态：

```text
首次打开 ── preview 设置 / Open as Preview ──────> 阅读态（1 组静态预览）
首次打开 ── dualPane 设置 / Preview to the Side ─> 编辑态（2 组源码加动态预览）
阅读态 ── Reopen as source file ────────────────> 编辑态（2 组）
编辑态 ── Open as Preview ──────────────────────> 阅读态（1 组）
编辑态 ── 侧边预览的 Open Source File ──────────> 编辑态（2 组，仅切换焦点）
编辑态 ── 关闭源码 ──────────────────> 阅读态（1 组）
编辑态 ── 关闭预览 ──────────────────> 规范回编辑态（2 组）
关闭当前 Markdown ───────────────────> 不再控制布局
```

编辑意图的优先来源：

1. 静态预览中的原生 “Reopen as source file”；
2. 源码编辑器中的原生 “Open Preview to the Side”；
3. 用户通过 “Reopen Editor With...” 明确选择文本编辑器。

插件应使用 `onDidChangeActiveTextEditor` 和 `tabGroups.onDidChangeTabs` 观察结果，并通过内部状态区分“首次打开源码”与“从阅读态切换到源码”。布局操作必须串行化并防抖，避免快速切换文件时出现重复面板、焦点跳动或旧任务覆盖新状态。

不提供“仅源码”第三状态。用户应通过源码编辑器的原生 “Open as Preview” 返回阅读态；在编辑态直接关闭预览时，插件会恢复预览，以维持编辑态严格双面板的产品约束。

## 6. 布局原则

- 阅读态必须将整个编辑区规范为恰好 1 个编辑器组，只让当前 Markdown 渲染预览占据可见编辑空间。
- 编辑态必须将整个编辑区规范为恰好 2 个编辑器组，源码位于 Group 1，渲染预览位于 Group 2。
- 两组的方向遵循 `workbench.editor.openSideBySideDirection`；进入编辑态前先收拢为单组，再由原生侧边预览命令创建唯一的第二组，不固定调用两列或两行布局命令。动态预览标签出现后调用原生 “Reset Editor Group Sizes”，避免下方 Group 2 只剩标题栏而没有可用内容区。
- 模式切换前，必须先安全保留多余编辑器组中的标签页和未保存内容，再合并编辑器组；不得以静默关闭不可恢复内容来换取目标布局。
- 使用 VS Code 原生布局命令完成组收拢，再由原生 Markdown 侧边预览命令按用户设置创建第二组，避免为不同标签类型和拆分方向分别实现脆弱的搬移逻辑。
- 如果某类标签页无法安全保留，则该实现不得进入发布版本；不为此维护一个违反 1/2 组约束的降级布局。
- 保持源码为主要编辑焦点；打开预览时不抢夺 Explorer、SCM 或源码编辑器焦点。
- 同一 URI 最多保留一个源码视图和一个渲染预览；重复命令应幂等。
- 不修改用户或工作区的 `workbench.editorAssociations`。插件应通过当前文档操作实现行为，避免永久改变 VS Code 的全局 Markdown 打开方式。

## 7. VS Code 1.131 原生交互

将 `engines.vscode` 从 `^1.91.0` 明确提升为：

```json
{
  "engines": {
    "vscode": "^1.131.0"
  }
}
```

本机 VS Code 1.131.0 内置 Markdown 扩展已确认以下原生命令：

| 界面动作 | 命令 ID | 原生行为 | 插件响应 |
| --- | --- | --- | --- |
| `Open as Preview` | `markdown.reopenAsPreview` | 把当前源码编辑器原位重开为静态 Markdown 预览 | 收拢为阅读态 1 组 |
| `Reopen as source file` | `markdown.reopenAsSource` | 把当前静态预览原位重开为源码编辑器 | 调用原生侧边预览并规范为编辑态 2 组 |
| `Open Preview to the Side` | `markdown.showPreviewToSide` | 在相邻组创建动态 Markdown 预览 | 确认并规范为编辑态 2 组 |
| `Open Source File` | `markdown.showSource` | 聚焦动态预览所关联的原源码编辑器组 | 保持编辑态 2 组，不重复创建预览 |

交互要求：

- 阅读态与编辑态之间的主要切换必须复用上述 VS Code 1.131 原生按钮和命令。
- 阅读态使用原生静态预览 `vscode.markdown.preview.editor`；编辑态使用原生动态侧边预览 `markdown.preview`。
- 不新增同义的 QuickLook 视图切换命令或重复的主要工具栏图标，不为 VS Code 1.130 及以下版本保留兼容命令或替代交互。
- 插件的职责是调用或观察原生交互结果，并把整个编辑区规范为阅读态 1 组或编辑态 2 组。

本机内置扩展源码表明：`markdown.reopenAsPreview` 和 `markdown.reopenAsSource` 通过 `reopenActiveEditorWith` 原位切换编辑器；`markdown.showPreviewToSide` 创建侧边动态预览；`markdown.showSource` 仅在原资源列重新显示源码。因此不依赖按钮文本猜测状态，而是根据 `TabInputCustom`、`TabInputWebview`、URI 和编辑器组结构识别结果。

## 8. 适用范围

第一阶段仅处理普通、已保存的 `file` Scheme Markdown 文档。

以下情况不自动进入阅读态或重排布局：

- Untitled 或尚未保存的 Markdown 文档；
- `TabInputTextDiff` 与 SCM Diff；
- `git`、`gitlens`、`vscode-local-history`、`review` 等虚拟或只读资源；
- 用户已经显式选择其他自定义编辑器的文档。

这些场景的首要意图通常是创建、编辑、比较或审阅，而不是普通阅读。先保留 VS Code 原生行为，比复用一套复杂的兼容分支更可靠。

## 9. 实现架构

已用新的 `markdownViewController.ts` 替换 `markdownDualPane.ts`，不保留旧实现的并行路径；纯状态转换位于 `markdownViewState.ts`。

职责拆分为：

- 纯状态决策：根据设置、URI、标签页状态和用户动作决定目标模式；
- VS Code 布局适配：负责打开、复用或关闭当前文档的源码与预览；
- 编辑器组规范化：安全保留现有标签页，并把整个编辑区收拢为目标 1 组或 2 组；
- 会话状态：记录 URI 当前模式、原生切换来源和最新操作序号；
- 原生交互桥接：调用或观察 VS Code 1.131 的四个原生命令及其结果，不提供重复的主要交互；
- 日志：记录触发原因、状态转换和被跳过的特殊场景。

状态决策写成无 VS Code 副作用的纯函数，并由现有 Node 测试框架覆盖；布局适配层需要在 VS Code 1.131 Extension Development Host 中完成实机验收。

## 10. 验收标准

1. `preview` 为默认值，普通 `.md` 文件打开后只显示渲染预览。
2. 阅读态下，整个 VS Code 编辑区始终恰好只有 1 个编辑器组。
3. 从阅读态点击 “Reopen as source file” 后，源码与动态实时预览同时可见，且整个编辑区始终恰好只有 2 个编辑器组。
4. `dualPane` 设置下，普通 `.md` 文件直接打开为源码加预览和 2 个编辑器组。
5. 收拢编辑器组时，其他标签页、未保存内容、Diff、自定义编辑器和终端标签不会丢失。
6. VS Code 1.131 的四个原生 Markdown 动作保持原有语义，不出现重复的插件工具栏主按钮。
7. 关闭源码可回到阅读态；编辑态关闭预览时会恢复预览，不产生“仅源码”第三状态。
8. 快速连续打开多个 Markdown 文件时，最终布局只对应最后一次有效操作。
9. 侧边预览中的 “Open Source File” 只恢复源码焦点，不改变双组布局。
10. `workbench.editor.openSideBySideDirection` 为 `right` 或 `down` 时都恰好只有 2 个编辑器组，且不存在空白第三组或被压缩到只剩标题栏的预览组；运行时修改该设置后，当前编辑态按新方向重新排列。
11. Diff、SCM、历史和 Untitled 文档保持 VS Code 原生行为。
12. 重复触发相同原生动作不会创建重复标签页或编辑器组。
13. 焦点保持稳定，不从 Explorer、SCM 或正在编辑的源码中被意外夺走。
14. 扩展只支持 VS Code 1.131 及以上，不包含旧版本兼容路径。
15. TypeScript 编译和 Node 单元测试通过；编辑器组收拢及四项原生交互在 VS Code 1.131 Extension Development Host 中通过人工验收。

## 11. 实施顺序

1. 将最低版本验证基线设为 VS Code 1.131，并以四个已确认的原生命令、标签页事件及布局命令建立测试基线。
2. 定义状态模型与纯决策函数，并先完成单元测试。
3. 实现安全的编辑器组收拢，覆盖普通文本、Diff、自定义编辑器、终端标签和未保存内容。
4. 实现阅读态 1 组布局和编辑态 2 组布局。
5. 接入 VS Code 1.131 原生静态预览、动态侧边预览与源码聚焦交互，不增加重复主交互。
6. 替换设置项并删除旧双面板实现。
7. 完成焦点、快速切换、手动关闭、组收拢和特殊资源测试。
8. 同步 README、README.zh-CN、CHANGELOG 和最低 VS Code 版本；发布版本号留到发布流程决定。

## 12. 决策边界

本文件建议的默认决策是：

- 默认采用 `preview`；
- 编辑时展开双面板；
- 默认不处理 Diff 与虚拟资源；
- 阅读态强制保持 1 个编辑器组，编辑态强制保持 2 个编辑器组；
- 用枚举设置替换旧布尔设置；
- 最低 VS Code 版本明确提升至 1.131，只复用已确认的原生视图切换交互，不维护旧版本兼容路径。

用户已于 2026-08-05 明确授权按本文实施并完成本地验证；提交和推送仍未授权。实现完成后应停止并等待用户实际测试。
