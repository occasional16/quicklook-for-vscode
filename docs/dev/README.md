# 开发工作文档

`docs/dev/` 保存需要开发者审阅的产品设计、重要决策和执行记录。开发者同时承担产品经理角色，因此文档首先服务于快速理解和决策，其次才是 AI Agent 的执行依据。

## 核心目的

每份文档只需回答四个问题：

1. 是否准确理解并完善了开发者的初步意图？
2. 推荐设计是什么，关键取舍和边界是什么？
3. 如何以可观察、可重复的方式验收？
4. 获得执行授权后，目前做到哪里、下一步是什么？

文档不是冻结的完整规格，也不能代替执行时对当前代码、依赖文档和最佳实践的核查。

## 写作原则

- **结论优先**：先给推荐方案和用户可感知行为，再补充必要理由；避免长篇复述背景和探索过程。
- **产品视角优先**：先用少量文字复述对开发者初步意图的理解，再给出完善后的用户体验、状态、规则、边界和取舍。代码结构只在影响决策或验收时说明。
- **最小充分**：只保留审阅、执行和验收所必需的信息。代码片段应短小，优先使用伪代码、接口或关键示例，不预写完整实现。
- **区分确定性**：明确标出已决定、待确认、假设和非目标，不能把 Agent 的推测写成既定要求。
- **验收具体**：使用可观察行为、自动测试和必要的人工步骤；长任务写明操作步骤及预期结果，避免“功能正常”“体验良好”等不可判定表述。
- **开发者操作可执行**：如果需要开发者在外部网站、桌面界面或账号中操作，必须单列“开发者操作”，写明前提、入口路径、逐项填写值、预期结果、需反馈的信息和安全注意事项；不能只写“配置”“授权”或“登录”。同时明确哪些步骤由 Agent 完成，避免职责不清。
- **进度可见**：长任务必须维护简短的执行清单、当前步骤、验证结果和阻塞项，不记录无助于判断的逐命令流水账。
- **保持开放**：文档约束目标、外部行为和验收标准，不锁死内部实现。执行时发现更简单或更可靠的实现，可以实时优化。
- **重大变化回审**：若新证据会改变产品行为、范围、外部契约或验收标准，应先更新文档并交由开发者审阅；仅内部实现优化无需反复确认。
- **一个权威版本**：同一决策优先更新现有文档；确需推翻核心方案时新建下一编号文档，并明确其与旧文档的关系。

一般文档正文建议控制在 50–120 行；复杂或长任务尽量不超过 150 行。超过时应先删除重复背景、推测性设计和低层实现细节，而不是默认继续扩写。必要证据可放在简短附录中。

## 状态与授权

文档状态和执行授权必须分开，避免把“认可设计”误解为“授权修改”：

| 状态 | 含义 |
| --- | --- |
| `Draft` | 等待开发者审阅，设计仍可调整 |
| `Approved` | 设计方向已确认，但仍以“执行授权”字段为准 |
| `In Progress` | 已获授权并正在实施 |
| `Pending Validation` | Agent 已完成实现和自身验证，等待开发者验收 |
| `Completed` | 验收通过，无待办项；等待下一次发布前清理 |
| `Superseded` | 已被另一份明确链接的文档取代；等待下一次发布前清理 |

安装依赖、破坏性操作、提交和推送仍遵循根目录 `AGENTS.md`，不能由工作文档自行扩大授权。

## 最小结构

除元数据外，默认只使用“结论与设计、待确认、验收、执行进度”四部分。没有实际内容的可选部分应删除。

```markdown
# 标题

| 字段 | 内容 |
| --- | --- |
| 状态 | Draft |
| 更新 | YYYY-MM-DD |
| 目标 | 一句话说明要解决的问题 |
| 执行授权 | 未授权 / 已授权（日期和范围） |

## 1. 结论与设计

- 用 1–3 句话说明对开发者初步意图的理解
- 推荐方案及其理由
- 用户可感知的主要行为
- 必须保护的约束和非目标
- 仅在影响决策时列出关键取舍或替代方案

## 2. 待确认

- 只列真正会改变结果、需要开发者决定的问题；没有则写“无”

## 3. 开发者操作（如需）

> 仅在需要开发者亲自操作外部系统、交互式界面或账号时保留。

1. 前提和准确入口
2. 按顺序点击的位置及各字段填写值
3. 每步完成后的可观察结果
4. 需要回复 Agent 的非敏感信息
5. 不得提供或保存的密码、token 等安全边界

Agent 可自行完成的步骤不要转嫁给开发者；开发者操作结束后，写明 Agent 将继续执行什么。

## 4. 验收

- [ ] 可观察的核心行为
- [ ] 关键边界和失败场景
- [ ] 自动测试、构建或静态检查
- [ ] 必要的开发者人工步骤及每步预期结果

## 5. 执行进度

> 未获执行授权时写“未开始”，不展开实施步骤。

- [ ] 实现核心行为
- [ ] 覆盖关键边界
- [ ] 完成验证并记录结果

当前：未开始
下一步：等待执行授权
验证：未开始
阻塞：无

## 必要技术说明（可选）

仅记录影响产品决策、外部契约、风险或验收的 API、数据结构和最小代码片段。
```

章节名称和数量可以按任务缩减，不要求机械套用模板。简单决策可以更短；长任务则必须保留验收和执行进度。

## 执行规则

1. Agent 先核查相关行为、代码和权威文档，再把开发者的初步想法完善为推荐设计。
2. `Draft` 阶段只讨论和更新文档，不因方案看似明确而自动实施。
3. 获得执行授权后，Agent 在动手前重新核对当前仓库与依赖能力；文档是方向和验收依据，不是盲目照抄的实现脚本。
4. 执行中持续维护简短进度；发现重大设计变化时暂停对应实现并回审，内部优化则直接进行并在完成时说明。
5. Agent 完成实现和自身验证后标记 `Pending Validation`；开发者验收通过后再标记 `Completed`。
6. 被替代的文档先标记 `Superseded` 并链接新的权威文档；完成或过期后按下述生命周期在新版发布前删除。

## 生命周期与 Git 留档

`docs/dev/` 是当前开发工作的工作区，不是永久文档档案。Git 历史承担归档职责：

1. 工作文档在设计、实现和验收期间保留，并随对应功能提交进入 Git 历史。
2. 文档完成、被取代或确认过期后，不立即移动到其他归档目录；先确保其最终内容已经提交，可通过 `git log -- <path>` 追溯。
3. 新版本发布前审查 `docs/dev/`：保留仍在进行、仍待验收或下一版本继续使用的文档；删除已完成、已取代或不再具有行动价值的文档。
4. 删除应列入发布准备变更并获得明确授权；发布提交同时记录删除结果，从而让仓库只保留当前有效工作文档，而完整历史仍可从 Git 恢复。
5. `docs/dev/README.md` 是长期有效的工作规范，不参与版本发布清理。

## 命名与语言

- 文件命名为 `<major>.<minor>-<sequence>-<topic>.<ext>`。
- `<major>.<minor>` 表示产品版本线；例如 `0.2.x` 使用 `0.2`。
- `<sequence>` 使用两位编号，从 `01` 起按创建顺序递增，新版本线重新编号。
- `topic` 使用简短英文 kebab-case；例如 `0.2-06-markdown-last-view-continuity.md`。
- 本 `README.md` 不参与编号。
- 正文默认使用中文；代码、命令、文件名和专有名词保留英文。开发者另有要求时，以其要求为准。
